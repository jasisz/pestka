## Clean loose-bound-variable finding

`../soundness-findings/loose-bvar-hadd-clean.ndjson` is a structurally ordered
export. The value of the safe definition `outParam` is an existing loose bound
variable. A later `HAdd` inductive block refers to `outParam`.

With a three-second per-checker limit:

| Checker | Result |
| --- | --- |
| Pestka native old | timeout |
| Pestka native next | timeout |
| Pestka VM | timeout |
| Pestka wasm-gc | runner error: generated module failed Wasmtime validation before Pestka ran |
| nanoda `a3ef25a` | panic: `no loose bvars allowed in infer` |
| sokonanoda `492227c` | internal error/panic: `loose bvar in infer` |
| nanoclo `01c537f` | panic: loose bvar in an empty environment |
| nanobruijn `7a04996` | panic: `dbj_idx=0 >= depth=0` |
| con-ron v4.35 | reject |

The machine-readable output, including bounded stdout/stderr, is in
`2026-10-27-loose-bvar-hadd.json`.

The native Pestka process stays at roughly constant memory and consumes one core.
Sampling places it in `whnfRun`/`whnfLoop`, reached from `ind_add.afterUniform`.
This is a termination/robustness issue, not evidence of invalid acceptance.

Lean Kernel Arena explicitly permits hand-crafted static exports with expected
outcome `reject`, classifies exit codes other than 0/1/2 as checker errors, and
places real checker crashes under `bugs/`. Nanoda's current Arena integration is
an explicit exception that maps every failure to reject, masking its panic.

## Fix

The reduction machine looked a bound variable in head position up with
`nthClo`, whose fallback past the environment was `#0` in an empty
environment: unfolding `outParam` met `#0` and looked it up again forever.
A bound variable past the environment is now stuck, dropped by the
environment's length, as `matTerm` and the second core's `nth` already
treat it. Pestka old, next and both, compiled and as wasm-gc under Node
(`bin/run-wasm`), now answer `rejected: outParam: the type checker met a
loose bound variable` in 0.24 s, and `tests/run.sh` runs every export under
`tests/soundness-findings` expecting a rejection.

The wasm-gc runner error above came from `aver run --wasm-gc` at Aver
163e4aea, whose wasm-gc module fails validation. At Aver eecfeecc the module
builds, and under Node it hung on this file before the fix like the
compiled build.

One worker, instructions retired against the same revision without the fix,

15.68 G to 15.66 G), `Init` 71.04 / 70.92 G to 70.93 / 70.90 G; wasm-gc
